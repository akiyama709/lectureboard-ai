# LectureBoard AI：発話中の自動板書から正式公開までの開発計画

更新日：2026年9月6日

状態：全体計画案．以下の新構成・数値目標は未実装・未検証であり，合格済みとは扱わない．

## 1．完成形と現在位置

　秋山さんがPowerPointで通常の講義を行うと，発話途中から文脈上重要な内容を判断し，その発話中に短い文字・簡単な図形をスライドの空白へ板書する．音声コマンドは不要で，原本は変更せず，人の手書きを優先する．文字起こし全体の確定や講義終了を待つ要約アプリにはしない．

　最終到達点は，既定の全5添付物・exact commitとの対応・未認証再取得検証を伴う，公開かつimmutableで非prereleaseのGitHub v1.0.0である．有料Apple Developer加入・機関名義は使わず，ad hoc署名及び未公証という配布条件を明示する．α・βという名前で中核要件の未達を公開しない．既存の公開要件はROADMAP及びv1-release-checklistを維持する．

　現在は段階1の起動・入力を調査中で，段階0の合成評価セット整備も残る．既存のbuild・単体テスト資産はあるが，2026年9月6日23時台の本人試用では管理スライドショー開始に失敗し，文字起こし開始時にTCCで終了した．通常起動での8秒確認は開始中のままで，マイク許可要求をログで確認した．音声認識・板書の回復は未確認．全体の完成率をテスト件数から計算しない．

## 2．構成判断（提案）

　現行AppModel.swiftの932行付近とContextualBoardEngine.swiftの53行付近には，最終認識結果だけを板書判断へ渡す境界がある．Speech側の既定8秒cycle・4秒final待ち期限は認識器の運用設定であり，実測遅延でも，毎回必ずその秒数待つ証拠でもない．ただし，現在のfinal-only構成で発話途中の即時板書が満たされるとは言えない．

　ImportanceScorerは語彙差・談話標識・反復等の固定特徴量を使う．これは再利用できる基準実装であるが，一般的な講義内容の理解や板書の有用性を証明するものではない．発話途中の同一認識仮説の改訂を，別の反復発話として数えないモデルが新たに必要である．

- 現行の管理開始・黒白role challengeを修正し続ける案：既存の厳格な結合を使えるが，開始時の対象確認が引き続き主要な実機リスクとなる．自動的に継続採用しない．
- PowerPointは本人が通常操作し，アプリは明示選択された対象を観測する案：優先して適合性を調べる．対象窓の結合，現在のスライド文脈，切替・移動・遮蔽時の抑止は別途必要であり，診断モードの安全条件を外すだけでは成立しない．
- 独自スライドビューアへ置き換える案：PowerPoint講義という既定要件を変更するため，本計画では採用しない．

　分離するのは開発中の責務と検証であり，実行時に「全文確定→要約→後から描画」と直列に待たせることではない．認識・文脈判断・短い単位の確定・描画を逐次つなぐ．重要性だけでなく，公開する内容の根拠と安定性も確認する．

## 3．全体の順序と合格条件

　段階1→2→3→4→5を中核の順序とする．段階4の観測方式の小さな実現性確認は，段階1〜3と独立して先行できるが，複数の長時間実機試験を並走させない．段階3の中間評価に不合格なら，描画や公開準備を増やす前に判断方式を修正する．段階5で実際の講義要件に合わなければ該当段階へ戻す．

　別ウィンドウは段階2の認識・判断・描画の切り分けに限って使える．最終的なPowerPoint余白への表示の代替にはせず，段階4以前の結果を「PowerPoint上で発話に同期した板書」と呼ばない．段階5を全機能・全書類の完成後まで延期しない．

## 4．即時性と内容の評価

　仮の開発目標として，板書対象となる短い語句・意味単位の発話終端から，実際に文字が見えるまでを中央値1秒以内・95パーセンタイル2秒以内と置く．これはユーザーとの確定合意でも達成済み性能でもない．発話終端の基準は全文章や認識器のfinal callbackではなく，評価セットで事前指定した短い単位とする．必要な後続文脈を待つ場合の遅延・保留も別途計上し，測定起点を後ろへ動かして遅さを隠さない．

- 録音開始時刻，部分結果受信，意味単位確定，重要度判断，描画要求，実際の可視表示を区別する．描画APIの呼出しだけで表示成功としない．
- 表示できた例だけの遅延集計に加え，見逃し，誤板書，重複，保留，訂正・撤回回数を全対象例について記録する．
- 否定・言い直し・不確かな認識で意味が反転する例，スライド切替と発話が重なる例，重要でないが語彙が新しい例を含める．
- 学生には未確定の全文を流さない．短く根拠のある内容から出し，公開済みの内容を頻繁に書き換えない．誤出力時の取消し方針は別に定義・試験する．
- 実音声・実画面の遅延測定はまず合成資料・許可された試験音声で行う．本人資料の内容をモデルへ読み込むことや，音声・画面を外部送信することをこの計画の承認から推定しない．

## 5．再利用，費用，担当，報告

　描画，配置，書出し，認識adapter，決定論的な評価関数，原本保護の境界及び対応テストは再利用候補とする．final-onlyの板書入口，同一発話の改訂管理，文脈判断の品質，通常起動時の権限，PowerPoint結合は実測に基づいて見直す．クラウドAPI契約・追加購入・Apple会費は前提にしない．ローカル方式で目標を満たせなければ，課金や機能縮小を勝手に選ばず，測定結果と選択肢を提示する．

　実装・合成試験・記録・公開物準備はCodexが担当する．秋山さんが必要なのは，代行できないOS認証，短い本人模擬講義，最終成果の評価及びexact成果物の公開承認である．通常の修正やテストごとに承認を求めない．他の作業・講義資料・権限設定は変更しない．

　不具合ごとに原因仮説・修正・回帰テスト・実機での再確認を1組として記録する．同じ失敗に対して根拠なく条件を追加し続けない．変更中は対応するテストと必要な統合テストを使い，全gate・配布物の作り直しはsource固定後にまとめる．初期の短い実動作が通る前に，追加の公開自動化や第三者監査を開発の中心にしない．

　報告は「現在：段階N／今回確認できたこと／未確認・障害／次の一手／公開までの残項目」に統一する．日付による完成予測は，段階1〜4の実測前には確約しない．最初の具体的な到達点は段階2の短い実演，次の本人試用は段階4合格直後とする．作業は確認のためだけに中断しないが，OS認証・本人試用・公開承認等の実際の境界は越えない．
